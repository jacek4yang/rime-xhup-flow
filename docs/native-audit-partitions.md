# 完整原生审计的确定性分区

本方案解决单 runner 穷尽审计可能超过六小时上限的问题，**不减少输入或断言**。
不是新的输入法质量结论，也不使正在运行的旧审计自动成为新版本证据。

## 输入和覆盖

`.github/workflows/full-regression.yml` 只生成一次包、CLI、固定源码 Lua 插件、
完整 static / extended / open manifests。extended/open 仍分别生成两次并逐字节比较。
部署、ASCII/标点/翻页、Lua、上下文与 doctor 门禁仍执行。

`tests/librime/audit_shards.py` 将每个 manifest 的非注释行按原始行号模 16 分配。
重复行保留，余数保留；每种输入的每个分区都必须非空。
分区计划绑定完整原清单 SHA-256、行数、每个分区 SHA-256/行数、
所有生成包文件、CLI 与插件字节，以及完整源码提交和 CI run/attempt。

16 个隔离 runner 各执行原来的完整审计脚本：
本分区全部静态码的干净对照、全部 extended/open 行、组句、
真实学习/重启、本分区全部静态码的学习后对照、CLI export/reset/import。
各分区独立从干净部署开始；同样的学习训练和哨兵会重复执行，
并非把一个用户数据库在多机间无锁共享。

## 失败关闭

- 子进程非零、超时、取消、跳过任一阶段都不能产生成功回执。
- 驱动清除外部聚焦/回放环境变量，避免意外只执行短测试。
- 仅退出零且包含完整阶段结束标记的日志可以生成回执。
- 汇总依赖全部 matrix jobs 成功，并要求恰好 16 份回执与日志。
- 汇总从原始 manifests 独立重新计算分区；验证计划、包、CLI、插件、
  提交/run、分区编号/行数/哈希和每份日志哈希，拒绝缺失、篡改或旧回执。
- 上传失败日志不等于上传成功回执。旧 run/attempt 不可混用。

回执是可信 CI 执行环境中的完成记录，不是数字签名，不声称可以防御
恶意 runner 伪造日志。输入资产、全部分区日志和最终覆盖 JSON 保留 14 天；
准备发布时应另外归档对应提交的完整证据，不能只引用一个绿色徽标。

## 本地检查与限制

`python3 -m unittest discover -s tests/librime -p test_audit_shards.py`
覆盖重复行、余数、缺失回执、输入/包/CLI/插件/分区变更、错误提交/run、
失败/不完整日志、非零进程和旧输出拒绝。这些是合成数据测试，
**不是 librime 穷尽通过证据**。

默认仍完整查询 141,138 个静态码、1,301,434 条 extended 关系和
1,000 条确定性 open 组合（实际计数由该提交生成的清单决定）。
最终覆盖 JSON 只在所有分区完成后产生；不硬编码历史数量代替实际输入校验。
此并行化不改变产品运行时、词典内容、候选上限或断言。
